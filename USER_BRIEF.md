# User Brief: Smart AI Gateway

**Who is the user?** You are an AI engineer running a support assistant on a small team. You want each request sent to the cheapest capable model, and problems caught early. You play two roles: a bank customer in Chat, then the engineer in Show details and Health.

**Where should you go?** Application: http://149.165.149.191:8080. README: https://github.com/sv642-hub/app-assignment-1#readme

**How should you get started?** (1) In Chat, send three or four banking questions, such as "My card has not arrived." Include one vague message and one that is not about banking. (2) For each reply, click Show details and read the trace: the route (standard or complex), the intent, the reply source and the format check. (3) Open Health and find which model has the most samples (its recent calls) and whether either one was disabled. (4) Optional: look at the Jev and Metrics screens, or open http://149.165.149.191:8080/docs and send one request through the API.

**What can it do, and what can't it do?** It is a demo of one workflow, not a general chatbot: it only handles banking support. It recognizes 77 banking intents and answers 10 of them from a fictional bank's policy cards; a recognized intent with no card gets "this demo does not cover that topic yet" (Reply source: unsupported_topic), and a message it cannot match to any banking topic gets a fixed "could not match" reply (Reply source: no_match). Please report which one you got. Jev routes each request to a small or large Qwen model, the reply's format is checked, and a model that keeps failing is disabled for a while. Real AI models run, and your messages are sent to TypeSafe, an outside service, so use only made-up details. Answers can be wrong even when the format check passes. Each message stands alone, so when asked for details, resend the full problem, and send one question per message. Your chat history stays in this browser tab after a refresh. The server also saves request details (route, intent, trace, timings) and the approved reply, so use only made-up details. There are no accounts or logins, and the link uses plain HTTP. Saved requests and the log of when models were disabled are kept when the app restarts, and a model that was disabled stays out of service until its hold ends. You cannot inject faults from the app, so expect a healthy system.

**What feedback are we seeking?** Was the app's purpose clear within a minute? Which trace fields helped, and which confused you? What would you need on the Health screen to trust the routing? If answers got worse, what would you check first? Please file each finding as one GitHub issue on our repository (README link above): feature tested, what you expected, what actually happened.
